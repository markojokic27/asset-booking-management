= 1. Introduction

This document defines the QA Test Plan for the Maurer Asset Booking Management — a web and mobile application designed to streamline the booking and management of working assets including laptops, parking spots, desks, meeting rooms, and books.

The system is developed as part of Maurer Internship 2026. This test plan covers all use cases defined in the system specification and includes 147 test cases across all major modules.

---

= 2. Test Strategy

== 2.1 Test Levels
[cols="1,2,2", options="header"]
|===
| Level | Description | Tools
| Unit Testing | Individual functions, services, repository methods | JUnit 5, Jest, Mockito
| Integration Testing | API endpoints, service-to-service calls, DB queries | Bruno
| System / E2E Testing | Full user flows across web and mobile UI | Selenium
| Manual Testing | QR scan hardware, biometric | Manual test scripts executed by QA team
|===

== 2.2 Test Types
[cols="1,2", options="header"]
|===
| Type | Coverage
| Functional | Core feature behavior per use case flows
| Negative / Edge Case | Invalid inputs, missing fields, constraint violations
| Security | Role-based access control, unauthorized access attempts
| Integration | Email delivery, Google Calendar sync, push notifications
| Regression | Re-run automated suite on every pull request via CI
| Exploratory | Unscripted testing of UI/UX and edge conditions
|===

== 2.3 Automation Strategy

Target: 85%+ automation coverage for functional and integration tests. The following categories will be automated:

- All API-level tests (booking CRUD, user management, asset management)
- Authentication flows including session timeout
- Double-booking concurrency checks
- Email and calendar integration
- Role-based access control verification

The following tests remain manual:

- QR code camera scanning — requires device camera
- Biometric login — requires physical biometric hardware

= 8. Entry and Exit Criteria

== 8.1 Entry Criteria
- Application build is successfully deployed to the test environment
- All required test data is prepared and available
- Test environment is stable and accessible
- All test cases are reviewed and approved

== 8.2 Exit Criteria
- All critical and high priority test cases have been executed
- No open Critical severity defects
- At least 95% of test cases passed
- All failed test cases have been documented and reported

= 9. Defect Management

[cols="1,2,2", options="header"]
|===
| Severity | Definition | Target Resolution
| Critical | System crash, data loss, double booking possible, security breach | Same day — block release
| High | Core feature broken, booking/approval flow fails | Within 2 business days
| Medium | Feature degraded, workaround available | Within 1 sprint
| Low | Minor UX issue, cosmetic defect | Backlog — next available sprint
|===

= 11. Risks

[cols="1,2,2", options="header"]
|===
| Risk | Impact | Mitigation
| Test environment unavailable | Testing blocked | Maintain a backup environment, notify team early
| Incomplete requirements | Missing test coverage | Regular sync with developers and stakeholders
| Time constraints | Reduced test coverage | Prioritize critical and high priority test cases
| Data dependencies between tests | Test failures due to state | Use independent test data per test, clean up after each run
|===
