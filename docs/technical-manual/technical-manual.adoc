== Project Overview

=== Purpose

The Asset Booking Management system is an internal web and mobile application developed
as part of the Maurer Internship 2026 programme. It allows company employees to discover,
reserve, and manage workplace assets — such as hot desks, meeting rooms, parking spots,
and shared equipment — through a unified interface.

Key capabilities:

* Browse and search all available workplace assets in real time
* Create, view, edit, and cancel bookings
* Prevent double-bookings through reservation conflict detection
* Book assets via QR code using the mobile interface
* Generate reports on asset utilisation and booking history
* Real-time visibility of which assets are booked and by whom

=== Architecture Summary

The system follows a three-tier client-server architecture:

[source]
----
┌───────────────────────────────────────────────┐
│                Browser / Mobile               │
│              React 19 Frontend                │
│         (served via Nginx in Docker)          │
└──────────────────────┬────────────────────────┘
                       │ HTTPS / REST (JSON)
                       │ JWT Bearer token
┌──────────────────────▼────────────────────────┐
│           Spring Boot Backend (Java 21)        │
│   REST API  │  LDAP Auth  │  Business Logic    │
└──────────────────────┬────────────────────────┘
                       │ JDBC
┌──────────────────────▼────────────────────────┐
│             PostgreSQL 18 Database             │
│         (schema managed via db_init.sql)       │
└───────────────────────────────────────────────┘
----

All three layers are containerised and orchestrated with Docker Compose.
The Makefile provides developer-friendly aliases for common compose commands.

security configuration, and domain models.

Contains all React components, pages, routing configuration, API client code,

The canonical SQL schema file used to initialise the PostgreSQL database.
Applied automatically when the `db` container starts for the first time.

The single source of truth for the REST API contract between frontend and backend.

Bruno collections used for smoke-testing the API both locally and in CI.

== Configuration

=== Spring Boot Profiles

The backend uses Spring Boot profiles to separate environment-specific configuration.
The active profile is controlled by the `SPRING_PROFILES_ACTIVE` environment variable.

[cols="1,3", options="header"]
|===
| Profile | Purpose

| `dev` | Local development. Enables detailed logging, relaxed security, and dev-friendly defaults.
| `prod` | Production. Enables stricter settings, reduced logging verbosity, and production datasource config.

|===

=== CORS Configuration

CORS is configured entirely via environment variables, making it easy to adjust per environment
without code changes:

[source,bash]
----
CORS_ALLOWED_ORIGINS=http://localhost:5173   # Dev frontend origin
CORS_ALLOWED_METHODS=GET,POST,PUT,PATCH,DELETE,OPTIONS
CORS_ALLOWED_HEADERS=*
CORS_EXPOSED_HEADERS=Authorization
CORS_ALLOW_CREDENTIALS=false
CORS_MAX_AGE=3600
----

For production, replace `CORS_ALLOWED_ORIGINS` with the actual deployed frontend domain.

=== JWT Configuration

The backend issues and validates JWT tokens for all authenticated requests.

[source,bash]
----
JWT_SECRET=<min 32 character secret>
JWT_EXPIRY_SECONDS=3600     # Access token: 1 hour
JWT_REFRESH_SECONDS=86400   # Refresh token: 24 hours
----

CAUTION: Use a cryptographically secure random generator for `JWT_SECRET` in production.
Do not reuse development secrets.

=== Observability / Tracing

The `SAMPLING_PROBABILITY` variable controls what fraction of HTTP traces are recorded
and exported to the tracing backend:

[source,bash]
----
SAMPLING_PROBABILITY=1.0   # Record 100% of traces (development)
SAMPLING_PROBABILITY=0.1   # Record 10% of traces (production)
----

=== Email (Mailtrap)

In development, outgoing emails are routed to Mailtrap so they never reach real recipients.
Configure with:

[source,bash]
----
MAIL_USERNAME=mailtrap_user
MAIL_PASSWORD=mailtrap_pass
----

Replace with production SMTP credentials when deploying.

== CI/CD Pipeline

The GitLab CI/CD pipeline is defined in `.gitlab-ci.yml` at the repository root.
It consists of five stages that run sequentially.

=== Pipeline Overview

[source]
----
.pre  →  compile  →  test  →  bruno  →  security
----

=== Stage Reference

[cols="1,2,3", options="header"]
|===
| Stage | Job(s) | What it does

| `.pre` | `debug:vars` | Prints key CI environment variables for debugging. Runs on `develop` branch only. Marked TODO for removal before production.
| `compile` | `backend:compile` | Builds the Spring Boot JAR using Maven, skipping tests. Caches `.m2` repository. Artifact: `backend/target/`.
| `compile` | `frontend:compile` | Installs npm dependencies and builds the React app. Caches `node_modules`. Artifact: `frontend/dist/`.
| `test` | `backend:test` | Runs all backend unit and integration tests via `mvn verify`. Publishes JUnit XML results.
| `test` | `frontend:test` | Runs frontend tests via `npm run test`. Marked `allow_failure: true`.
| `bruno` | `bruno:smoke` | Starts the backend against a live PostgreSQL service container, then runs the Bruno API collection as a smoke test. Publishes JUnit XML results.
| `security` | `backend-dependency-check` | Runs OWASP Dependency-Check on backend Maven dependencies against the NVD database.
| `security` | `frontend-package-vulnerabilities-check` | Runs `npm audit` on frontend packages at `--audit-level=high`.
| `security` | `osv-scanner` | Scans the entire repository using Google OSV Scanner for known vulnerabilities.
| `security` | `socket-security` | Scans supply-chain risks using Socket Security CLI.
| `security` | `snyk-scan-frontend` | Scans frontend dependencies with Snyk and publishes an HTML report.

|===

=== Stage Details

==== Compile Stage

Both compile jobs run in parallel. Each uses its own Docker image:

* Backend: `maven:3.9-eclipse-temurin-21`
* Frontend: `node:24-alpine`

Build artifacts are retained for 1 hour and passed to downstream jobs via GitLab artifact
sharing, avoiding redundant recompilation.

[source,yaml]
----
artifacts:
  paths:
    - backend/target/
  expire_in: 1 hour
----

==== Test Stage

Both test jobs depend on (`needs:`) their respective compile job, ensuring tests
only run after a successful build.

Backend tests use the Maven Surefire plugin and publish results as GitLab JUnit reports,
visible directly in merge request pipelines.

[source,yaml]
----
artifacts:
  reports:
    junit: backend/target/surefire-reports/*.xml
----

Frontend tests are currently marked `allow_failure: true`, meaning a test failure
will not block the pipeline.

==== Bruno Smoke Test Stage

The `bruno:smoke` job is the most complex job in the pipeline. It:

. Spins up a PostgreSQL 18 service container alongside the job.
. Installs OpenJDK 21, Maven, and the Bruno CLI (`@usebruno/cli@3.3.0`) into the Alpine image.
. Starts the Spring Boot backend in the background using `mvn spring-boot:run`.
. Polls the login endpoint every 3 seconds (up to 40 retries = ~2 minutes) until the backend is ready.
. Runs the Bruno test collection against `http://localhost:8080/API` using the `Admin` environment.
. Publishes JUnit XML results.
. Kills the backend process in `after_script`.

The job uses several CI-scoped secrets injected as variables:

[cols="1,2", options="header"]
|===
| Variable | Purpose

| `BRUNO_DB_PASSWORD` | PostgreSQL password for the CI service container
| `BRUNO_JWT_SECRET` | JWT secret used by the backend during CI runs

|===

This job runs on merge requests, the `develop` branch, and the `main` branch.
It is marked `allow_failure: true`.

==== Security Stage

Security jobs are designed to run without blocking the main development flow:

[cols="2,2,2", options="header"]
|===
| Job | Trigger | Notes

| `backend-dependency-check` | Nightly schedule, `main`, manual on `develop` | Uses `NVD_API_KEY`. Reports saved for 7 days.
| `frontend-package-vulnerabilities-check` | Nightly schedule, `main`, manual on `develop` | Fails on `high` or critical npm audit findings.
| `osv-scanner` | Nightly schedule, `main`, `develop` | Scans recursively (`-r .`). Report saved as JSON for 7 days.
| `socket-security` | Nightly schedule, `main`, `develop` | Uses `SOCKET_SECURITY_API_KEY` and `GITLAB_TOKEN`.
| `snyk-scan-frontend` | `feature/snyk`, `develop`, `main` | Uses `SNYK_TOKEN`. Saves JSON and HTML reports for 1 week.

|===

NOTE: Several jobs (`sonar`, `backend-dockerize`, `frontend-dockerize`, `playwright:test`,
`snyk-scan-backend`) are commented out in the current pipeline. These represent planned
or in-progress integrations.

== Architecture and Key Components

=== Frontend Architecture

The frontend is a React 19 single-page application (SPA).

==== Project Structure (frontend/src/)

[source]
----
frontend/src/
├── components/        # Reusable UI components (buttons, forms, modals, etc.)
├── pages/             # Top-level route views (LoginPage, DashboardPage, BookingPage, etc.)
├── hooks/             # Custom React hooks (data fetching, auth state, etc.)
├── services/ (or api/)# HTTP client functions that call backend API endpoints
├── context/ (or store/)# Global state management (auth context, booking context)
├── routes/            # React Router route definitions and guards
└── utils/             # Helper functions and constants
----

NOTE: The exact subfolder names may differ slightly. Verify against `frontend/src/`
in the repository for the current structure.

==== State Management

The application uses React's built-in context API and hooks for state management.
No external state library (Redux, Zustand) is indicated in the current `package.json`.

==== Routing

Client-side routing is handled by React Router. Protected routes verify the presence
of a valid JWT access token before rendering. Users without a valid token are
redirected to the login page.

==== HTTP Client

API calls are made using the browser's `fetch` API or a lightweight wrapper.
The JWT access token is attached to all authenticated requests as a Bearer token
in the `Authorization` header:

[source]
----
Authorization: Bearer <access_token>
----

When an access token expires, the client uses the refresh token to obtain a new
access token before retrying the original request.

=== Backend Architecture

The backend is a Spring Boot application following a layered architecture:

[source]
----
backend/src/main/java/
├── controller/        # REST controllers — handle HTTP requests and responses
├── service/           # Business logic layer
├── repository/        # Spring Data JPA repositories — database access
├── model/ (or entity/)# JPA entity classes mapped to DB tables
├── dto/               # Data Transfer Objects for API request/response bodies
├── security/          # JWT filter, LDAP config, Spring Security configuration
└── config/            # App-wide beans, CORS config, OpenAPI config
----

==== Authentication Flow

[source]
----
1. User submits credentials (username + password) to POST /API/v1/auth/login
2. Backend validates credentials against the LDAP directory
3. On success: backend issues a JWT access token + refresh token
4. Frontend stores tokens and includes access token in subsequent requests
5. Access token expires → frontend calls POST /API/v1/auth/refresh
6. Backend validates refresh token → issues a new access token
----

=== Database

The database is PostgreSQL 18. The schema is defined in `deployment/database/db_init.sql`
and applied automatically on first container startup.

For the current entity-relationship diagram, refer to `docs/database/ER.png` in the repository.

The application integrates with Grafana for dashboards and metrics visualisation.

The project follows an API-first methodology. The OpenAPI specification at
`openapi/assetBookingManagementOpenAPISpec.yaml` is the single source of truth
for all endpoints. Both frontend developers and API testers should refer to this
file when working with the API.

|===

| Local development | `http://localhost:8080/API/v1`

=== Authentication Endpoints

[cols="1,1,2", options="header"]
|===
| Method | Path | Description

| `POST` | `/auth/login` | Authenticate with LDAP credentials. Returns access + refresh JWT tokens.
| `POST` | `/auth/refresh` | Exchange a valid refresh token for a new access token.

== Troubleshooting for Developers

=== Docker / Compose Issues

==== Containers fail to start

Check that Docker is running and that no port conflicts exist:

[source,bash]
----
docker compose ps
docker compose logs <service-name>
----

Common port conflicts:

* Port `5432` — another local PostgreSQL instance may be running. Stop it or change `DB_PORT`.
* Port `8080` — another application may be using this port.
* Port `5173` — another Vite/dev server may be running.

==== Database is empty after restart

If you ran `make dev-clean` or `make prod-clean`, all Docker volumes were deleted,
including the database. The schema will be reapplied on the next `make dev`,
but any data you inserted manually will be lost.

==== Changes to backend code not reflected

In development mode, the backend does not have live reload by default.
Restart the backend container after making Java changes:

[source,bash]
----
docker compose -f compose.yaml -f compose.dev.yaml restart backend
----

Or bring everything down and back up:

[source,bash]
----
make dev-down && make dev
----

=== Frontend Issues

==== `npm ci` fails with peer dependency errors

The project uses `--legacy-peer-deps` to resolve peer dependency conflicts
between React 19 and the testing libraries. Always include this flag:

[source,bash]
----
npm ci --legacy-peer-deps
----

==== Frontend cannot reach the backend (CORS error)

Check that:

. The backend is running (`docker compose ps`).
. `CORS_ALLOWED_ORIGINS` in `.env` includes the frontend origin (e.g. `http://localhost:5173`).
. The backend has been restarted after any `.env` changes.

=== Backend Issues

==== JWT token errors (`SignatureException`, `ExpiredJwtException`)

* Ensure `JWT_SECRET` is identical between the process that issued the token
  and the process validating it. This is critical in multi-container setups.
* Ensure `JWT_SECRET` is at least 32 characters long.
* Check that system clocks are synchronised between containers if seeing
  premature expiry errors.

==== LDAP authentication fails

* Verify that the LDAP server is reachable from within the backend container.
* Check the backend logs for the specific LDAP error:
+
[source,bash]
----
docker compose logs backend | grep -i ldap
----

==== `mvn verify` fails locally but passes in CI

* Ensure your local Java version is 21: `java -version`
* Ensure your local Maven version is 3.9+: `mvn -version`
* Try clearing the local Maven cache:
+
[source,bash]
----
rm -rf backend/.m2/repository
mvn clean verify -Dmaven.repo.local=.m2/repository -Ddependency-check.skip=true
----

=== CI Pipeline Issues

==== Bruno smoke test fails in CI

. Check the pipeline log for the backend startup section.
  If the backend never reaches `READY=1`, the Spring Boot startup failed.
. Look for database connection errors — confirm `BRUNO_DB_PASSWORD` is set
  correctly in GitLab CI/CD variables.
. Check that `BRUNO_JWT_SECRET` is at least 32 characters.

==== Security scan jobs marked `allow_failure` are failing

Security jobs are non-blocking (`allow_failure: true`) by design for initial runs.
Review the artifact reports (HTML or JSON) to assess actual vulnerability severity
before deciding whether to remediate or suppress findings.

==== A job fails with "image not found" or registry errors

Ensure `CI_REGISTRY`, `CI_REGISTRY_USER`, and `CI_REGISTRY_PASSWORD` are available
in the pipeline context. These are injected automatically by GitLab for projects
with the Container Registry enabled.
